> 这份文档记录 captain 在派发任务前做的一次独立验证。
> 目的：确认「IR → x86-64 汇编」这条路走不走得通，避免成员在死路上浪费时间。

## 一、环境事实（实测，不是推测）

| 项 | 值 |
|---|---|
| gcc | 16.1.0 (MSYS2 ucrt64) |


## 三、两个必然踩的坑（已定位并给解）

### 坑 1：链接报 `undefined reference to WinMain`

生成的汇编**必须有 `.globl main`**，否则 MinGW 按 GUI 程序链接。

```asm
.intel_syntax noprefix
.text
.globl main          ← 少这行就链接失败
main:
```

试过 `-mconsole`，无效。`.def main; .scl 2; .type 32; .endef` 也可行，但没必要。

### 坑 2：参数搬运时寄存器宽度不匹配

```asm
mov DWORD PTR [rbp-16], rcx    ← Error: operand type mismatch
mov DWORD PTR [rbp-16], ecx    ← 正确
```

内存是 DWORD(32 位)，必须用寄存器的 32 位名：`rcx→ecx`、`rdx→edx`、`r8→r8d`、`r9→r9d`。

## 四、其他实测结论

- **不需要 `.seh_*` 异常处理指令**。完全不生成，链接和运行都正常。这是 codegen-dev 报告里标记的"待实测风险"之一，现已排除。
- 栈帧按 16 字节对齐，`sub rsp, 32` 起步。
- `call` 前留 32 字节影子空间：`sub rsp,32` / `call` / `add rsp,32`。
- 除法：`cdq` 扩展符号到 edx:eax，再 `idiv`。**`/` 结果在 eax，`%` 结果在 edx**。
- 比较：`cmp` + `setcc al` + `movzx eax, al` 生成 0/1。
- 有符号右移用 `sar` 而不是 `shr`。
- 逻辑非 `!x`：`test` + `sete` + `movzx`。

## 五、已知边界（当前实现跑不通）

> **本节已按 codegen-backend 的实测反馈修正。** 我原先的判断有 3 处不准，
> 逐条更正如下，保留原判断以示对照。

| 边界 | 原因 | 现状 |
|---|---|---|
| ~~5 个以上参数~~ | **已实现**。codegen-backend 做出来了，支持 8 参数与嵌套调用 | 可用 |
| 浮点 | IR 有字面量但无浮点运算指令 | 整套后端，不是补几条指令 |
| 数组/指针/结构体 | IR 是无类型的，无宽度无偏移 | 需要先给 IR 加类型字段 |
| 库函数（printf 等） | 需要链接 libc 且处理变参 | 单独阶段 |

**关于 `&&` / `||` 的语义缺陷**（重要）：

IR 里 `a && b` 是普通二元运算，两侧**都已被求值**。所以后端实现虽然能算出正确的布尔值，但**丢失了短路语义**：

```c
if (a && risky()) { }   // a 为假时 risky() 本不该被调用
```

对纯表达式无害，对含副作用的表达式有差异。彻底修需要在 `src/ir.py` 里把 `&&`/`||` 展开成跳转。

## 六、验证方法

每个程序都走完整链路：

```
.c 源码
  → csub 前端（预处理 → 词法 → 语法 → 语义 → IR）
  → 自写后端生成 .s
  → gcc 汇编链接成 .exe
  → 运行取退出码 A
同时：
  .c 源码 → gcc 直接编译 → 运行取退出码 B
比对 A == B
```

**为什么必须比对退出码**：程序返回 0 可能是算对了，也可能是没算但恰好是 0。只看"能跑"会严重高估能力。

## 七、探针代码

`_probe_codegen.py`（项目根目录）是这次验证的实现。

它**不是最终交付**，只是可行性证明。已知欠缺：

- 跳转标签名清洗不完整
- 未处理 5+ 参数
- 未做 caller-saved 寄存器保护（fib 能跑对是因为参数是立即数传递的，深层多参数调用可能出错）
- 未处理数组/指针/结构体

正式实现由 codegen-backend 在 `tools/codegen.py` 里做。

## 八、对本文档的更正（来自 codegen-backend 的实测反馈）

我（captain）在派发任务前写的探针和判断，有 3 处被成员的实测推翻。逐条记录：

### 更正 1：5 参数不是"做不了"，是"我没做"

我写"建议先只支持 4 个，超出明确报错"。codegen-backend 直接实现了栈上传参，
支持任意个数，并测通了 8 参数（4 个走栈）和"5 参数调用里再嵌套 5 参数"。

### 更正 2：我给调用方的偏移配方是错的

我建议 `sub rsp,32; push arg5`。他实测发现更精确的规则：

```
[rsp+0]  版 -> 109420074   ← 和我探针同款垃圾值
[rsp+32] 版 -> 15          ← 正确
```

因为 call 时 rsp 指向影子空间起点，影子空间占 `[rsp, rsp+32)`，
第 5 个参数必须**跳过**这 32 字节。

他采用了更稳的方案：出参区固定钉在帧底，大小 = 32 + 8×最大栈参数数，
构建时就能算出，于是 call 处 rsp 天然对齐，嵌套调用也不会互相踩。

### 更正 3：GAS 里 `;` 不是注释

我文档里写 `; 栈帧` 这种注释，在 GAS 语法下是**语句分隔符**。
首轮他 18 个程序全挂在这个错上（`junk at end of line`）。
Intel 语法下注释必须用 `#`。

### 补充：一个我没想到的静默错误

他的早期版本对 `1.5`、`p.x`、全局变量会**静默算出垃圾值**——被当成合法
标识符分配了栈槽，汇编能过、能跑、结果错。已全部改成明确报错，并做了
反向验证（7 类不支持输入 7/7 抛 CodegenError）。

这条给我的教训：**"能跑通"不等于"算对了"**。我探针里那些"通过"的用例，
可能有读未初始化栈内存的路径而我没发现。

## 九、最终实现的能力（以 tools/codegen.py 为准）

24/24 与 gcc 退出码完全一致，覆盖：
纯算术、函数调用、while/for/do-while、if-else、嵌套循环、fib 递归、
三函数互调、除法取模、位运算、三目、break/continue、一维数组、
指针 `&`/`*`、负除法截断、5/6/8 参数与嵌套栈传参。

明确报错而不静默算错的：浮点、字符串字面量、库函数、结构体、
全局变量、多维数组、指针算术缩放。
