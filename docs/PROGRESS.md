# csub 进展报告

本文记录 csub 从零到现在经历的各轮迭代，以及**每一轮是被什么代码逼出来的**。
写作原则：可复核的事实与推测分开写；数字都能用文中给出的命令复现。

最后更新：四轮迭代完成，第五轮（自我核查）已修复若干缺陷。

---

## 一、这个项目是什么，做到哪一步了

一个 C 子集的编译器前端 + 面向初学者的错误诊断器。产出两样东西：

1. 中文诊断：指出"能编译但会出事"的代码（未初始化、常量越界、`if (a = 1)`）
2. 三地址码 IR 与优化前后对比

**当前真实能力**（每项都能自己跑出来）：

| 能力 | 数字 | 复现命令 |
|---|---|---|
| 自建诊断用例 | 56 / 56 | `python tests/run_tests.py` |
| 有错代码召回 | 37 / 37 | 同上 |
| 合法代码误报 | 0 / 19 | 同上 |
| 与 gcc 判定真不一致 | 0 / 17 | `python tools/crosscheck.py` |
| IR 语义与真实运行一致 | 23 / 23（raw 与 opt 各自 100%） | `python tools/ir_verify.py` |
| 变异检出（主用例表） | 79 / 79 | `python tools/mutation_test.py` |
| 变异诊断行号准确 | 79 / 79（±2 行内） | 同上 |
| 变异检出（全量口径，含已知缺口） | 79 / 82 = 96.3% | 同上 |
| 第三方源码 error / warning | **0 / 0**（815 行、1436 行两份都是） | `python csub.py check examples/real_nmakehlp.c` |
| 示例文件崩溃 | 0 / 21 | 见「第四轮」 |

代码规模：`src/` 5 个模块，`tools/` 5 个工具，`tests/` 2 个文件，
`examples/` 21 个 C 源文件。

**做不到的**：见第八节（仍然存在的问题）与 README 的「已知边界」。
其中"有意取舍"与"精度限制"是设计选择，第八节列的是待办缺陷。

## 二、五轮迭代

五轮的划分依据不是时间，是**每次换了什么裁判**。这一点比日期重要：
每一轮新裁判都比上一轮更狠，暴露的都是上一轮裁判看不到的缺陷。

| 轮次 | 新增的裁判 | 逼出多少缺陷 |
|---|---|---|
| 一 | 真实作业代码能不能跑通 | 14 |
| 二 | 更大、更怪的第三方源码 | 20 |
| 三 | 把 IR 真正执行一遍，和 gcc 比结果 | 3 类 IR 缺陷 + 6 个连锁缺陷 |
| 四 | 随便什么输入都喂给它（模糊测试） | 8 类崩溃 |
| 五 | 逐条复核"已知边界"里每一条是否真的成立 | 3 条误报 + 2 个系统性检查缺口 |

## 三、第一轮：真实作业暴露的 14 个缺陷

**裁判**：一份 238 行的数据结构作业（约瑟夫环，`examples/hw_josephus.c`）。

**结论**：在拿到这份文件之前，工具在一个真实 C 文件上都跑不起来。

最致命的一条是 `#include` 直接词法报错——任何真实 C 文件第一行都是
`#include <stdio.h>`，不支持就等于工具在真实场景下第一秒就崩。

其余 13 条：

| # | 缺陷 |
|---|---|
| 1 | `#include` 直接词法报错（**最大的一条**） |
| 2 | 行号错位：预处理删行后，报的位置指向原文件的错误行 |
| 3 | `typedef struct` 不支持 → 数据结构作业全崩 |
| 4 | `f(void)` 表示无参，被当成一个 void 参数 |
| 5 | `(LinkList)malloc(...)` 类型转换不支持 |
| 6 | `int a = 1, b = 2;` 逗号多变量声明报语法错 |
| 7 | `do-while` 不支持 |
| 8 | 字符常量 `'n'` 不支持 |
| 9 | `NULL` 未识别为常量宏 |
| 10 | `scanf("%d", &v)` 里的 `v` 被当未初始化读取 |
| 11 | `sizeof(Node)` 里的 typedef 名被当变量 |
| 12 | 多维数组 `int a[N][N]` 不支持 |
| 13 | 科学计数法 `1e9` 不支持 |
| 14 | `static` / `unsigned long` 等存储类与多词类型不支持 |

**这一轮的教训**：用例集里全绿说明不了任何事。工具的真实可用性由
第一个真实文件决定，而这个文件的第 1 行就能证明工具不可用。

## 四、第二轮：被第三方源码逼出来的 20 个缺陷

**裁判**：换更大的代码。一份 815 行的 Tcl 构建工具（纯 Windows API，
`examples/real_nmakehlp.c`），一份 1436 行的 numpy f2py 模块
（`examples/real_fortranobject.c`）。

**结论**：从 113 个误报收敛到 0 error。

20 条缺陷里，最值得记录的两条：

**类型名识别**（`(*(init))()` / `(ternaryfunc)fn`）。
`(*(init))()` 是函数指针调用，`(ternaryfunc)fn` 是类型转换，两者在语法上
无法区分——都形如 `(标识符)` + 表达式。最后的解法是让 parser 记录
**已声明的变量名**：括号里的名字如果是见过的变量，就绝不是类型转换。
这个判据是唯一可靠的，其他启发式都会在真实代码上翻车。

**输出参数索引**（`WriteFile(..., &dw, NULL)`）。
只有第 4 个参数是输出。早期把"第 3 个起都算输出"，于是 `NULL` 被当成左值
报 E1。改成精确 0 基索引。这条之所以重要，是因为它揭示了一类系统性问题：
**语义检查里的"保守近似"会在真实代码上变成误报**，"宁可多报"不是安全的选择。

其余 18 条（浮点后缀、调用约定修饰符、多行宏续行、初始化列表、
C99 指定初始化器、相邻字符串拼接、数组形参、函数指针 typedef、
switch/case、goto 标签、三目、逗号表达式、常量表达式数组长度、
可变参数、函数指针形参、无穷无尽的类型名、字符串里嵌未定义宏、
全局变量零初始化、输出参数索引）详见 README 的「第二轮精进」一节。

## 五、第三轮：被"真跑一遍"逼出来的缺陷

**裁判**：不是新代码，是新的验证方式——把 IR 解释执行一遍，
和 gcc 编译后真实运行的退出码比。

**结论**：静态检查全过、全部真实文件零崩溃的情况下，IR 语义是错的。

### 5.1 三个 IR 缺陷

| 缺陷 | 症状 | 修复前 | 修复后 |
|---|---|---|---|
| `const_fold` 无视控制流 | 循环里的 `i = i + 1` 被固化成 `i = 1`，循环不前进 | 13 / 23 不一致，5 例死循环 | 23 / 23 |
| do-while 回边极性反 | 该"条件为真跳回循环头"，写成了 ifFalse | `dowhile` raw=0 vs gcc=6 | 一致 |
| switch 负常量 case 悬空标签 | 分发与展开各调一次 `gen_expr`，生成两个不同临时变量 | `goto` 指向不存在的标签 | 一致 |

三条的共同点必须单独说：**它们全都是自己写进 `src/ir.py` 的翻译/优化逻辑，
此前只做静态检查，从没运行验证过**。`const_fold` 用一张线性推进的常量表做
传播，完全不看控制流——代码读起来"很像那么回事"，但循环里一跑就废。

这类缺陷的可怕之处在于：它不是崩溃，是**安静地给出错误结果**。
如果没有解释执行器，它永远不会被发现。

修复方式：常量传播只在基本块内进行，遇到 `label`/`goto`/`if`/`ifTrue`/
`return`/`call` 就清空常量表。

### 5.2 六个连锁缺陷

修 IR 验证的过程中，一跑真实文件就现形的一批：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 成员访问基表达式非裸标识符时无限递归（`(*p).a`、`mk().a`） | 整份文件 `RecursionError` 崩溃，不是报诊断 |
| 2 | `&x` 被当成"读取 x" | `struct S *p = &s;` 之后再用 `s` 误报未初始化 |
| 3 | `check_lvalue` 侧漏了外部符号容忍 | `&PyArray_Type` 走左值路径时仍报 E1 |
| 4 | `va_arg(argp, int)` 的类型参数无法解析 | parser 在 `int` 上直接崩——**1436 行文件卡住的真正原因** |
| 5 | `va_list argp` 由 `va_start` 初始化的语义没实现 | 后续使用误报未初始化 |
| 6 | 函数指针调用 `(*(getter))(&flag)` 的参数没视为可能写出 | 误报未初始化 |

**第 1 条值得单独记一笔，因为它是"自测 100% 但真实文件一跑就崩"的典型**：
E15（结构体成员拼错）功能刚加完，在自造的小例子上全部正确，
但 `check_member()` 把整个 Member 节点传回 `check_expr()`，
形成 `check_expr -> check_member -> check_member_base -> check_expr` 的死循环。
小例子里基表达式都是裸标识符（`n.dat`），走不到那条回落路径；
真实文件里全是 `fp->defs[i].rank` 这种，一跑就崩。

**第 4 条是整份 1436 行文件卡住的真正原因**：`va_arg(argp, int)` 的第二个
参数是**类型名**而不是表达式，parser 把它当表达式解析，在 `int` 上崩。
一条语法分支的缺失，让一份大文件完全无法分析。

## 六、第四轮：模糊测试

**裁判**：随便什么输入。字节级变异、token 汤、边界输入，每例独立子进程
（超时能真杀、`RecursionError` 不污染后续用例）。

**结论**：764 个用例 + 128 个 CLI 用例里发现 **8 类去重后的崩溃**
（共 18 次命中，0 次死循环），全部是 `RecursionError` 或 `ValueError`，
即**学生看到的是 Python traceback，而不是"你的代码第几行有问题"**。

| # | 异常 | 位置 | 最小输入 | 当前状态 |
|---|---|---|---|---|
| 1 | `ValueError: invalid literal for int() with base 16: '0x'` | `parser.py` `parse_primary` | `t n(){0x` | **仍复现** |
| 2 | `RecursionError` | `parser.py` `parse_ternary` | 150 层括号 | **仍复现** |
| 3 | `RecursionError` | `parser.py` `parse_unary` | 120 层嵌套函数调用 | **仍复现** |
| 4 | `RecursionError` | `semantic.py` `check_expr` | 深下标链 `t[0][0][0]...` | 已不崩 |
| 5 | `RecursionError` | `parser.py` `expect` | 400 层裸花括号 | **仍复现** |
| 6 | `RecursionError` | `ir.py` `gen_expr` | 深成员链 `b.b.b.b...` | 已不崩 |
| 7 | `RecursionError` | `parser.py` `parse_postfix` | 深三目 `1?1?1?...` | **仍复现** |
| 8 | `RecursionError` | `parser.py` `parse_primary` | 深 if 嵌套 `if(1)if(1)...` | 已改为正常拒绝 |

（"当前状态"是用 `tools/fuzz_artifacts/crash_*.c` 这 8 个复现文件
对当前代码重跑得到的。第 4、6 条不崩是因为成员链与下标检查被修过；
第 8 条变成正常的 ParseError。**其余 5 条仍在**。）

第 1 类 `0x` 是确定的功能缺陷：十六进制字面量没检查后面有没有数字。
其余 7 类都是**递归下降解析器没有深度上限**——输入合法但极深时，
Python 的递归栈先于任何语法检查耗尽。

另有一类没进上表但同样确认：超长整数字面量（超过 4300 位）触发
`ValueError: Exceeds the limit for integer string conversion`，
是 Python 3.11+ 的整数转换限制，不是 csub 自己的逻辑，但同样会抛 traceback。

**这一轮的意义**：前三轮的裁判都假设"输入是合法的 C 文件"。
模糊测试去掉了这个假设，暴露的是**前端对畸形输入的鲁棒性**，
这些缺陷不影响正常使用，但会让工具在演示现场直接抛 traceback。

**代价评估**：这 8 类里没有一条能通过"合法 C 文件"触发——
`0x` 是非法字面量，其余都是几百层嵌套。所以它们**不是当前能力的缺陷，
是鲁棒性缺陷**，优先级低于第八节里的成员链与结构体初始化问题。

## 六之二、第五轮：复核自己的"已知边界"

**裁判**：把前面几轮写下的每一条"已知边界"逐条拿去实测。

**结论**：清单里 3 条不成立，且其中 2 条背后压着更大的缺口。

这一轮没有引入任何新工具，只是**把已经写下来的结论重新验一遍**。
最典型的是两条警告：`real_nmakehlp.c` 的 W3 和 `real_fortranobject.c` 的 W6，
文档里一度写成"检查终于生效了"。实际去读那两处源码：

```c
/* nmakehlp.c:798 —— 两个操作数都是 sizeof，不可能丢小数 */
for (i = 0; i < (sizeof(paths)/sizeof(paths[0])); ++i) {

/* fortranobject.c:531 —— i 下一行就用了 */
int i = 0;
if (fp->defs[i].name == NULL) {
```

**两条都是误报。** 顺着 W6 追根因，发现成员链 `fp->defs[i].name` 里的
下标表达式根本没有被检查——这一个缺口同时造成"误报 W6 + 漏报 E1 + 漏报 E13"。
追 W3 的过程中又发现行号口径问题：`str.splitlines()` 把换页符也当换行，
`real_nmakehlp.c` 里 csub 报第 808 行、gcc 报第 798 行。

三条缺陷的共同点是：**它们都藏在"看起来是好消息"的表象后面**。
"警告从 0 变成 1"看起来像能力提升，实际是误报开始冒头。

修复与复核方式见第九节。

## 七、一个反复出现的模式

五轮下来，同一个模式出现了五次：

> **用自己构造的输入测，全绿；换一个不受自己控制的裁判，立刻出问题。**

| 轮次 | 自己构造的输入 | 换掉的裁判 | 结果 |
|---|---|---|---|
| 一 | 手写用例集 | 真实作业代码 | 14 个缺陷，包括"根本跑不起来" |
| 二 | 一份真实作业 | 第三方大型源码 | 从 113 个误报到 0 |
| 三 | 静态检查 IR 文本 | 解释执行 + gcc 对比 | 13 / 23 IR 语义错误 |
| 四 | 合法 C 程序 | 任意字节序列 | 8 类崩溃 |
| 五 | 自己写的"已知边界"清单 | 逐条拿去实测复核 | 3 条误报被当成能力、2 个系统性缺口 |

这不是巧合。**自己构造的输入天然只能覆盖自己想到的情况**，
而缺陷恰恰长在没想到的地方。

第五轮尤其说明问题：那份"已知边界"清单是**我自己写的**，
里面每条我都以为已经核实过。真去逐条复现时，才发现
两条被我标成"有效警告"的东西其实是误报，而它们背后还压着
两个更大的缺口（行号口径、成员链下标）。

也就是说：**连"我知道自己不知道什么"这件事，也需要被验证。**

所以这个项目的指标表里，真正有分量的从来不是"自建用例 100%"，
而是这几行：

- gcc 真不一致 **0 / 17**（裁判是独立实现）
- IR 与真实运行 **23 / 23**（裁判是执行结果）
- 第三方源码 **0 error / 0 warning**（裁判不是我写的代码）
- 示例崩溃 **0 / 21**

自建用例的 100% 在五轮里一次都没能预测出上面任何一条。

## 八、当前已知问题（按优先级）

这一节是**待办**，不是已完成的能力。每条都经过实测确认。

> **状态更新**：本节原先列的 8.1（行号口径）、8.2（成员链下标）、
> 8.3（W3 的 sizeof 误报）已在后续修复中解决，实测复核通过。
> 为确保"改了什么、怎么验的"可追溯，修复过的三条移到第九节，
> 这里只保留**仍然存在**的问题。

### 8.1 成员链里 Index 之后的数组越界不报（已确认，未修）

```c
struct d { int rank[2]; };
struct fp { struct d *defs; };
/* p->defs[0].rank[99] —— 不报 E13 */
```

对照实测：

| 写法 | 是否报 E13 |
|---|---|
| `t.cell[24]`（直接成员数组） | 报 |
| `p->cell[24]`（指针成员数组） | 报 |
| `t.sub.cell[24]`（二级成员数组） | 报 |
| `p->defs[0].rank[99]`（成员链走过一次下标之后） | **不报** |

缺口不在"长度为 2 的数组"识别不出来，而在**成员链中间夹了一次 `Index`**
之后，后续成员的类型推导断掉了。修的时候要注意别把已经正常的
`p->cell[24]` 弄坏。

### 8.2 结构体整体赋值后按值传参仍报 E2（已确认，未修）

```c
struct S { int a; };
int f(struct S s);
int main() {
    struct S s;
    s.a = 1;      /* 所有成员都写了 */
    f(s);         /* 仍报 E2：使用了未初始化的变量 's' */
}
```

只跟踪成员级写入，不跟踪"整体已完整初始化"。

### 8.3 模糊测试发现的 5 类崩溃仍在（已确认，未修）

见第六节的"当前状态"列。其中 4 类是解析器无递归深度上限，
1 类是 `0x`/超长整数字面量的 `ValueError`。
最后一次复核（当前代码，`tools/fuzz_artifacts/crash_*.c` 逐个重跑）：
**5 类仍复现**，2 类已不崩，1 类改为正常拒绝。

**优先级判断**：这些都需要几百层嵌套或非法字面量才能触发，
正常 C 文件碰不到，所以排在 8.1、8.2 之后。

### 8.4 已完成但边界明确的

- **有意取舍**：全大写标识符、首字母大写函数名的拼写错误查不出来。
  放宽是为了压住真实代码里的假错误（`NPY_INTP_FMT` 这类宏）。
- **精度限制**：数组元素的初始化状态不跟踪。
- **不支持**：`enum`、`union`、位域、局部函数指针变量、函数宏展开、
  复杂条件编译、机器码生成。

## 九、本轮修掉的（附修复与复核方式）

本节记录已经解决的问题。**留在这里是为了让"改了什么"可追溯**，
而不是宣称能力。每条都给出复核命令，修没修好可以自己验。

### 9.1 行号口径偏差

**问题**：`src/preprocess.py` 用 `str.splitlines()` 切行。`splitlines()`
会把换页符 `\x0c`、`\x0b`、`\x85`、`\u2028` 等也当行分隔符，
而编辑器（VS Code / vim）和 gcc 只认 `\n`。

`examples/real_nmakehlp.c` 含 10 个换页符：`splitlines()` 得 825 行，
按 `\n` 切得 816 行，**差 9 行**。当时 csub 报 W3 在第 808 行，
而在按 `\n` 口径的第 798 行注入错误，gcc 报第 798 行。

**修复**：`preprocess.py` 导出 `split_lines()` 只按 `\n` 切，
`csub.py`、`render.py` 统一改用它，口径一处定义。
修这个又暴露一个被掩盖的问题：`\x0c` 之前被当换行符吞掉，词法器根本不认它，
一旦保留就报"非法字符"——已把 `\f`/`\v` 加入合法空白。

**复核**：往 `real_nmakehlp.c` 按 `\n` 口径的第 798 行注入一个未声明变量，
csub 与 gcc 应都报第 798 行。

### 9.2 成员链中下标的检查缺失

**问题**：`fp->defs[i].rank` 里的 `i` 完全没有被检查：

- 误报 W6「变量 `i` 声明后从未使用」
- 漏报 E1：`fp->defs[zz].rank` 的未声明变量不报
- 漏报 E13：同位置的常量越界不报

根因在 `check_member()` 逐层走成员链时没有对 `Index` 节点的下标调 `check_expr`。
`real_fortranobject.c:531` 那条 W6 就是它。

**修复**：`check_member()` 增加 `check_member_chain_exprs()` 遍历链上各表达式。

**复核**：`o.defs[zz].rank` 应报 E1；`fp->defs[i].rank` 应不再报 W6。

**残留**：成员链中间夹了一次 `Index` **之后**的数组越界仍不报，
见 8.1。这是同一个函数里的另一半问题，没修完。

### 9.3 W3 在 `sizeof` 相除上误报

**问题**：`sizeof(paths)/sizeof(paths[0])` 是取数组长度的标准惯用法，
两个操作数都是 `sizeof`，相除不可能丢小数，W3 却报了。
`real_nmakehlp.c:798` 那条 W3 就是它。

**修复**：W3 对两侧都是 `sizeof` 的除法豁免。

**复核**：`int p[3]; ... (sizeof(p)/sizeof(p[0]))` 应不再报 W3。

### 9.4 修完后的直接效果

`real_nmakehlp.c` 与 `real_fortranobject.c` 从 0 error / 1 warning
变成 **0 error / 0 warning**，而且是**真干净**（误报被修掉），不是掩盖。

同时保留了对照：`lab_optime.c:41`（W5 浮点比较 + W3 整数除法）与
`lab_optimize.c:40`（W5 + W3）仍是**有效警告**——
`counter += (5 - 1) / 4` 确实整数除法得 1，浮点循环变量与常量比较确实有风险。
**"零警告"只在这两份第三方文件上成立，不是全局状态。**

### 9.5 其他已修项

| 曾经的问题 | 修法 |
|---|---|
| 成员访问基表达式非裸标识符时无限递归崩溃（`(*p).a`、`mk().a`） | `check_member_base` 只对剥完 Member 后的内层表达式做检查，不再把 Member 节点丢回 `check_expr` |
| `const_fold` 无视控制流，循环里 `i = i + 1` 被固化成 `i = 1` | 常量传播只在基本块内做，遇 `label`/`goto`/`if`/`ifTrue`/`return`/`call` 清空常量表 |
| do-while 回边极性反（该 ifTrue 写成 ifFalse） | 改用 `ifTrue` |
| switch 负常量 case 生成悬空标签 | 预先求值一次、缓存标签名，分发与展开严格复用 |
