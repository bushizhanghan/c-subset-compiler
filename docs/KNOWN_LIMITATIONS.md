# 已知限制清单

> **这份清单是「不要再当成 bug 修」的边界。**
>
> v1.0 之后，只有「真实学生作业又撞到新问题」才会改动。
> 下面这些明确**不修**——它们是设计取舍，不是缺陷。
>
> 最后更新：2026-10-22

---

## 一、判据

判断一个新发现的问题该不该修，只问一句：

> **这个写法，目标用户（大二学生写作业）会写吗？**

| 情况 | 处理 |
|---|---|
| 真实学生代码撞出崩溃 / 误报 | ✅ 修（这是核心场景） |
| 学生作业常见的语法不支持 | ✅ 修（但先确认真的常见） |
| 资深开发者才会用的语法 / 扩展 | ❌ **记进本清单，不修** |
| 需要「理解程序意图」才能判断的错误 | ❌ 结构上做不到，见第三节 |

---

## 二、明确不支持（不再当成 bug）

### 2.1 前端语法

| 语法 | 现状 | 为什么不修 |
|---|---|---|
| **宽字符字符串 / 常量** `L"中文"` / `L'A'` | 解析失败 | 学生作业基本不用；实现要改词法 + 语义 + 后端全链路 |
| 三字符组 `??=` / `??/` | 静默吞掉（不报错） | C23 已移除，现实中不存在 |
| `_Generic` 泛型选择 | 当普通调用吞掉 | C11 特性，学生作业不用 |
| `_Complex` 复数 | 当普通声明吞掉 | 学生作业不用 |
| 内联汇编 `asm` / `__asm__` | 当普通语句吞掉 | 工具不生成汇编注入 |
| 嵌套函数（GCC 扩展） | 当普通块吞掉 | 非标准 C |

**「吞掉」的含义**：不报错、不崩溃，但相关语义检查会跳过。
这比报错安全——宁可漏检，不可误报。

### 2.2 后端代码生成

只影响 `tools/codegen.py` 真正编译成 exe。
**`csub.py check`（查错）不受任何影响。**

| 特性 | 现状 | 报错信息 |
|---|---|---|
| 数组作函数参数 `int sum(int a[], int n)` | 明确报错 | "数组参数退化为指针的语义未实现" |
| 函数内定义结构体 `struct P{...} p;` | 明确报错 | "没有 main 函数"（连带） |
| 全局数组 `int g[4];` | 明确报错 | "全局数组带布局的后端尚未支持" |
| 多维数组 `int a[2][3]` | 明确报错 | 不支持 |
| 函数返回结构体 | 明确报错 | 不支持 |
| `char**` 多级指针的完整语义 | 部分支持 | 视具体用法 |

**原则**：宁可明确报错，不静默算错。
（"静默算错比报错更糟"是后端设计的硬约束，代码里有多处注释强调。）

## 三、结构上做不到（静态分析的上限）

这五类**不是实现问题，是技术路线决定的**。
换成任何静态分析工具（包括 clang-tidy）都做不到。

### 3.1 算法 / 数学逻辑错误

```c
// 完美数：因子成对出现，漏了配对的 num/i
if (num % i == 0) { ans += i; }        // 只加了小因子

// 三数之和：结构错了
while (left < right) { ... }           // left/right 从不移动，死循环
```

**为什么做不到**：语法、类型、控制流全对。
错误在于"没理解这道题的数学事实"。

### 3.2 内存泄漏 / 资源泄漏

```c
int* ans = malloc(n * sizeof(int));
if (k == 0) { return; }                // 提前返回，ans 没 free
free(ans);
```

**为什么做不到**：需要路径分析（每条 return 前检查）+ 别名分析
（p 和 q 是否指向同一块）。真实代码里提前 return 到处都是，
误报风险远超收益。

**gcc 也要 `-fanalyzer` 才查这个**，且误报率不低。

### 3.3 跨行语义不一致

```c
while (x != 0) {
    int y = x % m;      // 按 m 进制取位
    x /= 10;            // 却按 10 进制右移
}
```

**为什么做不到**：每一行单独都合法。
错误在于两行之间的**意图不一致**。
同样的代码形状有对有错（`n%10; n/=10` 就是对的）。

### 3.4 运行时越界（长度来自输入或参数）

```c
bool f(int* nums, int numsSize) {
    if (numsSize < 3) {
        if (nums[1] > nums[0]) { ... }   // numsSize==1 时越界
    }
}
```

**为什么做不到**：`nums` 是 `int*` 参数，长度完全未知；
`numsSize` 的范围是题目约束（"1 ≤ numsSize ≤ 10^5"），
静态分析拿不到。需要符号执行或运行时检查。

### 3.5 算法复杂度

```c
for (i = 1; i <= n; i++) printf("%d", sum(i));   // sum 内部又循环 i 次
```

**为什么做不到**：需要跨函数分析循环嵌套深度。
很多场景循环里调函数是必要的，误报风险高。

## 四、有意取舍（不是 bug，代价已接受）

### 4.1 全大写标识符被当成外部宏

```python
# _is_likely_external_macro()
# 全大写 / 含连续 3 个大写段的标识符 → 当成"来自看不到的头文件的宏"
```

**依据**：`real_fortranobject.c`（1400 行 numpy C 扩展）里
`NPY_INTP_FMT`、`Py_RETURN_NONE` 这类宏出现十几次，
不放宽就是十几条假错误。

**代价**：全大写的拼写错误查不出来。
**判断**：这个取舍值得。

### 4.2 未知 typedef 一律放行

```c
npy_int a = 1;          // npy_int 是 typedef，真实宽度看不到
LinkList head;          // LinkList 是 struct Node*
COORD pos;              // COORD 是 Windows API 结构体
```

**规则**：类型名不在 `int/char/long/short/float/double/void`
白名单里时，**所有类型检查跳过**。

**依据**：看不到真实宽度就猜 = 制造假错误。
实测 `LinkList` 被 W26 误报、`npy_int` 被 W23 误报。

**代价**：自定义 typedef 的类型错误查不出来。

### 4.3 `sizeof` 的值按占位处理

预处理阶段不真算 `sizeof`，只保证不报错。

**代价**：`char buf[sizeof(struct S)]` 这类数组长度检查不了。

### 4.4 错误恢复只做单层

```c
char a[16] = {...}     // 漏分号
char b[64];            // 被当成"新函数返回类型+名字"
while (...) { ... }    // 报"期望类型声明"
```

**现状**：`parse()` 以「顶层声明」为恢复单元。
一次语法错误会导致后续声明被错误切分。

**代价**：漏分号的代码，后面只能恢复第一层。
要做到语句级恢复是更大的工程。

**收益**：比"遇到第一个语法错误就整份放弃"好得多
（stu_17 从"1 条语法错误、后面全废"变成"3 条诊断"）。

### 4.5 W17（没有 main）整个删掉

早期报 WARNING，后来发现 **LeetCode/PTA 的函数题全都没有 main**，
连续三份样本每份都报一次，纯噪音。

**判断**：宁可漏掉"忘了写 main"，也不给每份函数题加噪音。

## 五、已知的误报风险点（已修，但要留意）

| 场景 | 曾经的错误 | 现状 |
|---|---|---|
| `scanf` 传数组名 | 误报成漏 `&` | 已修（stu_11） |
| `n/2` 递归除法 | 误报"改成浮点" | 已豁免（stu_02） |
| 函数片段无 main | 报 ERROR 挡住诊断 | 已删规则 |
| 多字符常量 `'ans'` | 判成"字符常量未闭合" | 已修（stu_21） |
| 空定义宏 | 展开成 `0` 伪造出常量语句 | 已修（stu_13） |
| 未知 typedef | 格式串/指针检查误报 | 已豁免 |
| 可变参数 `...` | 被当成参数名 | 已修（stu_20） |
| 可变参数函数调用 | E4 要求参数个数严格相等 | 已修（stu_20） |
| `char ds[5]="WASD"` | 声明初始化被判 E18 | 已修（stu_25） |
| 二维数组 `m[i]` | 类型推成 char 值 | 已修（stu_25） |
| `(float)j` | cast 类型被当成 int | 已修（stu_26） |
| `#ifndef X` 头文件保护 | 整块内容被丢弃 | 已修（stu_39） |
| `sizeof` 返回类型 | 当成 int，W23/W2 连带误报 | 已修（stu_38/40） |

**每次加新规则，这 13 条都要复验**——回归测试里有对应用例。

## 六、v1.0 之后的改动策略

### 会修

- 真实学生代码撞出**崩溃**
- 真实学生代码撞出**误报**（正确代码被报成错误）
- 学生作业里**高频出现**的语法不支持

### 不修

- 本清单第二节列出的语法
- 本清单第三节列出的五类问题
- 冷门 C 语法 / 编译器扩展
- 需要「理解意图」的判断

### 怎么验收一个改动

```bash
python tests/run_tests.py          # 不能低于 176/176，误报必须 0
python tools/err_bench.py          # 不能低于 34/42
python tools/student_eval.py       # 样本误报必须 0
python tools/mutation_test.py      # 不能低于 79/79
python tools/ir_verify.py          # 必须 23/23
python tools/codegen.py --selftest # 必须 60/60
```

**六套全绿才算改对了。** 任何一项退化都不合并。

## 七、为什么这份清单重要

一个工具成熟与否，不看它查得多全，
看它**对自己的边界有多诚实**。

- 用户知道「这些查不到」→ 不会误信 → 不会因为漏检而怪工具
- 维护者知道「这些不修」→ 不会被无穷的 issue 拖死
- 21% 的检出率写在明面上 → 没人期待它替代人

**把边界写清楚，比多修三个规则更有价值。**
