# student_real —— 真实学生代码样本库

这个目录存**真实学生手写的 C 代码**，不是 AI 编的用例。

它的唯一用途：验证 csub 在真实学生代码上的**误报率**和**检出率**。
没有它，所有"防误报"的设计依据只是开源代码——而开源代码是
被作者调教过编译器的代码，和学生代码是两个物种。

## 命名规则

```
stu_NN_简短描述.c
```

- `NN` 从 01 开始递增，不留空号
- 描述用英文小写 + 下划线，例如 `stu_03_josephus.c`
- 如果来自某个同学，加后缀：`stu_03_josephus_zhangsan.c`

## 每个文件必须带头部注释

```c
/*
 * 来源：自己写的 / 同学的 / 课程示例 / OJ 提交
 * 场景：什么作业（如"约瑟夫环"、"链表反转"）
 * 已知问题：如果有老师批注或自己知道的问题，写在这里；
 *           没有就写"未知"
 * 规模：约多少行、几个函数
 */
```

`已知问题` 那一栏很重要。**如果知道哪里有错，csub 应该报；
如果不知道，csub 报出来的就都是待人工确认的疑似误报。**

## 我需要多少

分三个阶段，越往后越有价值：

| 阶段 | 数量 | 能回答什么 |
|---|---|---|
| **第一批** | 5-8 个 | 会不会一上手就误报？基本可用性 |
| **第二批** | 累计 20 个 | 误报率能否压到可接受？哪些规则在误报？ |
| **第三批** | 累计 40-50 个 | 检出率、错误类型分布，能否给出可信结论 |

### 什么代码最有价值（按优先级）

1. **被老师批改过的作业** —— 有标注的错误，是金标准。即使只有错在哪几句话也极其有用。
2. **OJ 上 WA（答案错误）的提交** —— 能编译、能跑、结果错，正是 csub 的目标场景。
3. **自己觉得写得没问题的代码** —— 用来测误报。这个和 1 一样重要。
4. **得了低分的作业** —— 错误密度高。

### 什么代码价值低

- 太短的（< 30 行）——覆盖不到函数间交互
- 教科书上的标准例题 —— 那是规范代码，和开源代码同类
- 从网上抄的模板 —— 作者水平未知，混入噪声

## 我拿到之后会做什么

1. 逐个跑 `python csub.py report stu_XX.c`
2. 把结果分三类：
   - **真检出**（确实有问题，且 csub 报对了）
   - **疑似误报**（csub 报了，但代码其实没问题）—— 这类必须修
   - **漏报**（学生知道有错，csub 没报）
3. 汇总成 `docs/STUDENT_EVAL.md`，包含：
   - 误报率、漏报率（分规则统计）
   - 每条规则的"可信度"评级
   - 需要修的具体规则和原因

## 什么时候算"够了"

当满足这两个条件之一：

- **误报率降到 0** 且累计 20 个以上样本
- 或者：误报率稳定在某个数字，且每个误报都有明确根因和修复方案

到那时，这个工具才算真的验证过。

## 一个请求

**不要为了给我"好看的"代码而筛选。**

写得烂的、混乱的、风格奇怪的代码，价值最高。我需要看到真实的错误分布，而不是经过挑选的样本。
