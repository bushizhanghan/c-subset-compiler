## 1. 判卷口径（先说清楚，否则下面的数字没法读）

每个用例文件头部按固定格式写明规格：

```c
 * 期望 csub 报什么：E2 使用未初始化的变量 'sum'。   ← 与旧 28 个文件兼容的格式
 * 期望码：E2                                       ← 可选，显式写明，优先级更高
 * 分类：未初始化                                     ← 可选，缺省时按工具内置表回溯
```

`期望码` 有三种取值，判卷规则各不相同，**必须分开看**：

| 期望码写法 | 含义 | 判定 | 本轮条数 |
|---|---|---|---|
| `E2`（明确） | csub 有这条诊断，就应该报出来 | 命中 → 检出；报了别的 → 误报；没报 → 漏报 | 24 |
| `未实现` | csub 目前**根本没有**这条诊断，写下来是为了让缺口可见 | 必漏报；若报了别的反而记误报（防止靠无关警告蒙混） | 12 |
| 没写（旧用例的"一条 XX 警告"） | 模糊期望 | 报了任何诊断即算检出（**偏松**） | 6 |

「三态」定义：

- **检出** —— 实际诊断里出现了期望码
- **漏报** —— csub 一声不响
- **误报** —— 报了东西，但报的不是这个用例要考的那类错误

「崩溃」单列，任何一条都算底线失败。本轮 **0 条**。

### 同一个结果，三种口径

只报一个数字会误导人，所以三个都列出来：

| 口径 | 说明 | 数值 |
|---|---|---|
| 总检出率（42 例） | 含「未实现」和「模糊期望」用例 | **22/42 = 52.4%** |
| **严格口径（24 例）** | 只算期望码明确、且 csub 确实有这条诊断的用例 | **21/24 = 87.5%** |
| 旧 28 例 / 新增 14 例 | 分组看更能说明问题 | 20/28 = 71.4% ／ **2/14 = 14.3%** |

**怎么读这三个数字**：

- **87.5%（严格口径）不等于"csub 能查出 87.5% 的真实错误"**。这个子集是
  「csub 已经有对应诊断规则」的题目，相当于只考了已经学会的那部分。
  它衡量的是**规则实现的正确性**，不是能力覆盖面。
- **52.4%（总检出率）也不等于能力水平**，因为分母里塞了 12 个
  「明知没实现」的用例——那是我故意选来暴露短板的，不是随机抽样。
- **14.3%（新增用例）才是本轮最该看的数字**。新用例是按"当前覆盖薄弱"
  定向挑的，这个低值精确对应短板所在，不是抽样偏差造成的偶然。

一句话：**csub 对"查表能定的符号类错误"接近满分，对"要跨语句推理的行为类
错误"基本为零。** 这条分界线在 42 个用例上依然成立，而且比上一轮更清楚。

## 4. 漏报清单——按根因分类，不是"不支持"

20 条漏报可以归到 **5 个根因**。同一根因下的用例是同一处改动就能一起修好的。

### 根因 A：数组下标只折常量，没有区间分析（7 条）

| 用例 | 现象 |
|---|---|
| `err_03_off_by_one` | `for (i=0; i<=5; i++) a[i]`，写 `a[5]` 越界 |
| `err_12_reverse_index` | `for (i=0; i>=0; i--)` 首次访问 `arr[-1]` |
| `err_15_uninit_arr_read` | `int a[4]; printf("%d", a[2]);` 读未初始化元素 |
| `err_16_string_no_terminator` | 字符数组写满但没写 `'\0'` |
| `err_33_strcpy_overflow` | `char s[4]; strcpy(s, "abcdef")` 栈溢出 |
| `err_34_array_bound_write` | `for (i=0; i<=5; i++) a[i]`（变量下标，同 03 不同起始） |
| `err_35_string_missing_nul` | 5 字节全填可见字符，无 `'\0'` |

**根因**：`check_oob()` 第一行是 `const_int(e.idx)`，下标折不成常量就直接返回。
变量下标、循环区间、字节级写入这三种都落在这条早退之外。
修它需要**区间分析**（循环变量取值范围）+ **字符数组元素级状态**，是本清单里
工作量最大的一类，7/20 的漏报归它。

### 根因 B：类型推导退化成 `Type.base` 字符串（3 条）

| 用例 | 现象 |
|---|---|
| `err_05_char_int_confusion` | `char c; c = "A";` 无诊断 |
| `err_20_pass_array_by_index` | 数组传给 `int` 形参，无诊断 |
| `err_32_wild_ptr_escaped` | `g = &inner;` 把局部地址存进全局指针 |

**根因**：`check_expr` 只返回一个字符串（`"int"` / `"char*"`），
指针层级和数组维度在表达式层就丢了，所以 `check_assign_compat`
只能写死 float→int 一条判据。根因 B 和 A 有一部分重叠：
`err_33` 的 `strcpy` 目标容量也需要"这是一个长度已知的数组"这个信息。

### 根因 C：没有"循环变量的推进性/方向"分析（4 条）

| 用例 | 现象 |
|---|---|
| `err_04_loop_never_advance` | `while (i<10)` 循环体没有改动 `i` |
| `err_28_infinite_loop` | `for (i=0; i<10; i--)` 增量方向反了 |
| `err_40_infinite_growth` | `for (i=10; i>0; i++)` 反方向（与 28 互为镜像） |
| `err_39_neg_abs_overflow` | `abs(INT_MIN)` 溢出（需要常量求值 + 边界取反） |

**根因**：`check_stmt` 的 While/For 分支只检查条件再递归进循环体，
不收集"条件里的自由变量是否在循环体里被朝收敛方向修改"。
这是**跨语句的数据流推理**，`Analyzer` 现在是一次遍历 + 符号表状态，
没有 reaching definitions / interval analysis 这类机制。
gcc 对这一类**一条都不报**（见 §6），所以这是纯增量价值。

### 根因 D：生命周期/存储类别没有状态跟踪（5 条）

| 用例 | 现象 |
|---|---|
| `err_29_use_after_free` | `free(p)` 之后再读 `p[0]` |
| `err_30_double_free` | 同一指针 `free` 两次 |
| `err_36_block_scope_escape` | 块内变量地址逃出块 |
| `err_37_static_counter_misuse` | `static` 局部变量跨调用保留状态（语义陷阱） |
| `err_42_stray_semicolon` | `if (cond);` 把 if 变成空语句 |

**根因**：这五条各需要一个"状态机"——堆指针的 已分配/已释放 状态、
块作用域的生存期边界、存储类别差异、条件后紧跟空语句的形态识别。
`err_31` 之所以能检出，正是因为 `W9` 是**专门为"return &局部变量"这一个
形态写的特例规则**；`err_32`（存进全局指针）和 `err_36`（逃出块作用域）
是同一类错误换了个到达路径，特例规则就接不住了。
**这说明"加特例"和"建机制"的差别**——特例能快速见效，但覆盖不了变体。

### 根因 E：常量求值不做溢出检查（1 条）

| 用例 | 现象 |
|---|---|
| `err_38_int_overflow` | `int big = 2147483647; big + 1` |

**根因**：`const_int()` 用 Python 的任意精度整数求值，
`2147483647 + 1` 在 Python 里是合法的 2147483648，
所以"溢出"这件事在折叠过程里根本不发生。要报它必须显式比对
int 的表示范围。`err_39` 属于同一根因的取反形态（归在 C 里）。

## 5. 本轮的一个意外：队友的 `W9` 正好接住了我的用例

写 `err_31_return_local_addr` 时，我判定"csub 没有这条诊断"，头部写的是
`期望码：未实现`。跑工具时它却报了：

```
[WARNING W9] 19:5: 返回了局部变量 'local' 的地址，该地址在函数返回后失效
```

查 `git diff src/semantic.py`：队友在同一时间给 `src/semantic.py` 加了
`check_return_local_addr`，正是为 `return &local` 这个形态写的。

我把 `err_31` 的期望码改成了 `W9`——**用例头部必须如实描述被测工具的实际
行为，不能为了维持一个"漏报"结论而把已经检出的用例写成漏报**。

这件事本身是个有用的数据点：**同一类错误（悬空指针）下，
"函数直接返回局部变量地址"被接住了，"存进全局指针"（`err_32`）
和"逃出块作用域"（`err_36`）没有**。这就是 §4 根因 D 里说的
"特例 vs 机制"的差别，工具把这个差别原样暴露了出来。

也说明：`src/` 正在被别人改动，本轮的检出率是**某一时刻的快照**。
重跑 `python tools/err_bench.py` 就能拿到当时的真实值——这正是把验证做成
工具的意义，手工统计做不到这一点。

## 6. 与 gcc 对照（`gcc -fsyntax-only -Wall -Wextra`）

42 个用例全部跑过（gcc 16.1.0）。**已滤掉缺 `#include` 造成的噪音**：
这些用例为了能被 csub 直接跑都没有 `#include <stdio.h>`，
由此产生的 `-Wimplicit-function-declaration`（47 条）和
`-Wbuiltin-declaration-mismatch`（46 条）与被测错误无关，会淹没对照表。
其余所有诊断**一条不滤**（含无 flag 的硬 error）。

### 四象限汇总

| 归类 | 数量 | 用例 |
|---|---|---|
| **两边都报** | 14 | 02, 09, 10, 17, 18, 19, 21, 23, 24, 25, 26, 27, **31**, 41 |
| **gcc 报 / csub 漏** | 3 | **05, 20, 42** |
| **csub 报 / gcc 放行** | 8 | 01, 06, 07, 08, 11, 13, 14, 22 |
| **两边都没报** | 17 | 03, 04, 12, 15, 16, 28, 29, 30, 32, 33, 34, 35, 36, 37, 38, 39, 40 |

### 三条结论

**1. 「gcc 报 / csub 漏」3 条 —— 这是真缺口，值得修。**

- `err_05`（`char c = "A"`）、`err_20`（数组传 int 形参）：
  gcc 有完整类型树，csub 的类型推导在表达式层退化成字符串（根因 B）。
- `err_42`（`if (cond);` 空语句）：gcc 的 `-Wempty-body`
  + `-Wmisleading-indentation` 双报，csub 一条不报。

这 3 条的共同点是**gcc 用局部信息就能判定**，不需要跨语句推理。
说明 csub 在"静态可判定的信息"这一侧还有欠账，不是能力边界问题。

（`err_31` 原本也在这张清单里，队友本轮加的 `W9` 把它补上了——
现在它落在「两边都报」。下一轮复跑时这张表还会变。）

**2. 「csub 报 / gcc 放行」8 条 —— 这是差异化价值，是产品存在的理由。**

`err_01`（未初始化）、`06`（浮点比较）、`07`（整数除法）、
`08`（野指针）、`11`（函数名拼错）、`13`/`14`（常量越界）、
`22`（缺 return）——gcc 加了 `-Wall -Wextra` 依然一声不响。
这些都是学生作业里高频、且**能编译通过**的错误。

**3. 「两边都没报」17 条 —— 全行业盲区，是机会不是缺陷。**

17/42 = 40% 的用例，gcc 完全放行，csub 也没接住。
其中 `err_33`（strcpy 栈溢出）、`err_29`（use-after-free）、
`err_38`（整数溢出）是真实世界里 CVE 和事故的主要来源。
gcc 要靠 ASan / UBSan 这类**运行时**工具才抓得到，
而 csub 的定位是**编译期就告诉学生"这行会出事"**——
这块地没人占，也最难占（需要 §4 的根因 A/C/D 那套数据流机制）。

### 为什么这个对照有价值

它把"漏报"拆成了两种性质完全不同的东西：

- **gcc 也报的漏报**（3 条）→ **能力缺陷**，抄 gcc 的做法就能修，优先级高。
- **gcc 也不报的漏报**（17 条）→ **产品定位**，不是"做得不如 gcc"，
  而是"这条路谁都还没走通"。用 gcc 的标准要求 csub 会得出错误结论。

不做这张表，很容易把 20 条漏报一律当成"csub 不行"；
做完这张表，其中 17 条的准确描述是"csub 和 gcc 一样不行，
但这正是 csub 应该去的地方"。

## 9. 给后续轮次的建议（按性价比排序）

1. **补 `if (cond);` 空语句检测**（`err_42`）。gcc 用
   `-Wempty-body` + `-Wmisleading-indentation` 两条规则就能报，
   csub 只需在 `check_stmt` 的 If 分支判断 `then` 是不是空语句。
   **改动最小、gcc 已证明可判定、学生高频**，最该先做。

2. **`check_assign_compat` 补 `char* → char`**（`err_05`）。
   现在只认 float→int 一条判据。补上就能接住 `char c = "A"`，
   连带把 `Str` 的类型与"字符串字面量"区分开。

3. **`const_int()` 加 int 范围检查**（`err_38` / `err_39`）。
   现在用 Python 任意精度整数求值，"溢出"在折叠过程里根本不会发生。
   加一个范围比对即可，成本很低。

4. **字符数组元素级状态 + `strcpy` 容量检查**（`err_33` / `err_35` /
   `err_16`）。需要先有"这是一个长度为 N 的字符数组"这个信息，
   与第 5 条共享同一套类型信息。

5. **实参类型比对 + 指针层级**（`err_20` / `err_32` / `err_36`）。
   根因 B，改动面最大（要重做表达式层的类型表示），
   但它是 4 条漏报的共同根因，收益也最大。

6. **循环变量区间分析**（`err_03` / `err_04` / `err_12` / `err_28` /
   `err_34` / `err_40`）。根因 A + C，8 条漏报归它，
   工作量最大，且 gcc 完全不做——**这是差异化价值的主战场，
   但短期出不来的话，前面的 1~5 条性价比高得多**。
