# 真实错误作业验证集（examples/err_*.c）

> 这是 csub 第一次拿**"本来就是错的学生代码"**当裁判。
> 在此之前，全部验证都建立在两类代码上：
>
> 1. **能正常编译的代码**（`hw_josephus.c`、`real_nmakehlp.c`、
>    `real_fortranobject.c`、`mutation_bank.c` 全部 0 error）——
>    验证的是「不误报」；
> 2. **人工注入的变异**（`tools/mutation_test.py`，79/79 检出）——
>    验证的是「能查错」，但错误是我自己设计好再注入的。
>
> 真实学生的错误分布此前**完全没有测过**。这一批 28 个用例补的就是这个缺口。
>
> **本目录只新增文件，未修改 `src/`、`tests/`、`tools/` 下任何已有文件。**
> 发现的漏报全部只记录、不改代码。

## 3. 漏报清单与根因猜测

以下 10 条漏报按根因归类。**只记录，未修改 `src/`。**

### A. 循环边界与死循环倾向（4 条，0 检出）

| 用例 | 现象 | 根因猜测 |
|---|---|---|
| `err_03_off_by_one.c` | `for (i = 0; i <= 5; i++)` 写 `a[5]`，无诊断 | `check_oob()`（`src/semantic.py:861`）第一行就是 `ci = const_int(e.idx)`，**下标不是常量表达式就直接 return**。`i` 是循环变量，无法折叠成常量，于是整条越界检查被跳过。 |
| `err_12_reverse_index.c` | `for (i = 0; i >= 0; i--)` 第一次访问 `arr[-1]`，无诊断 | 同上。且本例的循环条件 `i >= 0` 不是常量条件，`check_condition()`（`:514`）的 W5 只对「条件本身是 `Num`」报警，`i >= 0` 是 BinOp，不命中。 |
| `err_04_loop_never_advance.c` | `while (i < 10)` 循环体无 `i = i + 1`，无诊断 | **没有这条检查**。`check_stmt()` 的 While 分支（`:467`）只调 `check_condition` 然后递归进循环体，不分析「循环变量在循环体内是否被修改」。要做需要收集条件里的自由变量，再查循环体是否存在对它的赋值。 |
| `err_28_infinite_loop.c` | `for (i = 0; i < 10; i--)` 增量方向反了，无诊断 | 同上，且更细：要比较增量方向与条件的收敛方向。属于**死循环方向分析**，当前完全没有对应机制。 |

**共同根因**：E13 只覆盖常量下标；变量下标的越界检查、循环变量推进性检查、
增量方向检查都没有实现。这三件事都需要**跨语句的数据流推理**，
而当前 `Analyzer` 是「一次遍历 + 符号表状态」的轻量模型，没有需求集
（reaching definitions / interval analysis）。

### B. 类型混淆（2 条，0 检出）

| 用例 | 现象 | 根因猜测 |
|---|---|---|
| `err_05_char_int_confusion.c` | `char c; c = "A";`，无诊断 | `check_assign_compat()`（`:433`）**只判断一种不兼容**：`target.base in ("int","char") and src_type == "float"`。`Str` 在 `check_expr` 里返回 `"char*"`（`:542`），`char* → char` 不在判断范围内。 |
| `err_20_pass_array_by_index.c` | `int sum_all(int v)` 却传 `a`（数组），无诊断 | **实参类型完全没检查**。`check_call()` 的最后一段（`:1107`）只 `for a in call.args: self.check_expr(a)` 数个数，从不比对形参类型与实参类型。数组实参的类型推导也丢信息：`Index`/`Ident` 路径返回的是 `.base`，不体现「这是个数组/指针」。 |

**共同根因**：类型系统只推导到 `Type.base`（一个字符串），指针层、数组层在
表达式层就丢了。`check_assign_compat` 的判据因此只能写死 float→int 一条。

### C. 未初始化（进阶形态，2 条）

| 用例 | 现象 | 根因猜测 |
|---|---|---|
| `err_02_scan_missing_amp.c` | `scanf("%d", v)` 漏 `&`，无诊断 | 这是**最有意思的一条**。`STD_FUNCS["scanf"]` 配的是 `"varargs_out"`，`check_call` 里 `is_out = i >= 1`，于是第 2 个参数被当成「输出位置」。而输出位置的处理分支（`:1050`）只对 `UnOp("&", Ident)` 和裸 `Ident` 标记已初始化——**裸 `v` 恰恰命中 `elif isinstance(a, Ident)` 这一支，直接被标记成 initialized**，从此不再报 E2。也就是说，**为了不误报 `scanf("%d", &v)` 而设计的宽容规则，把 `scanf("%d", v)` 这个真实错误一起吃掉了**。 |
| `err_15_uninit_arr_read.c` | `int a[4]; printf("%d\n", a[2]);`，无诊断 | README 已记录的有意取舍：数组声明时直接 `sym.initialized = True`（`:430`），避免「整块被函数写入」（`GetFullPathName(szPath, n, szCwd, NULL)`）场景误报。代价是元素级初始化状态完全不跟踪。 |

### D. 其他行为陷阱（2 条）

| 用例 | 现象 | 根因猜测 |
|---|---|---|
| `err_16_string_no_terminator.c` | `char s[3]; s[0..2]='a'..'c'` 缺 `'\0'`，无诊断 | 需要「字符数组整体被逐元素写满但没写 `'\0'`」的判断。当前对字符数组没有任何元素级跟踪（同 C 类根因）。 |
| `err_22_missing_return.c` | `int sign(int x)` 在 `x == 0` 分支无 return，无诊断 | W8（`:379`）**只对 `fn.name == "main"` 生效**。`block_returns()` 这个工具函数本身已经能判「块末尾是否有 return」，但只在 main 上调用。把它推广到所有非 void 函数是低成本改动。 |

### E. 一条「检出了但话说错了」的

`err_06_float_eq.c` 判为检出，但值得记录：报的是

```
[WARNING W5] 17:9: 条件表达式是浮点数，与 0 直接比较可能因精度出错
```

源码是 `if (a + b == c)`，**根本没有和 0 比较**。触发它的是 `check_condition`
里 `if t == "float"` 这一支（`:527`）——`a + b == c` 的类型被推成 float，
于是走了「浮点与 0 比较」的分支。诊断结论（有精度风险）是对的，
**但提示语与源码不符**，学生照着提示去看会找不到「与 0 比较」的地方。
建议后续把这条提示按 `cond` 的实际形态分流：裸标识符/整体是浮点才说
「与 0 比较」，`==`/`!=` 关系运算应说「浮点数不要用 == 判断相等」。

## 4. 与 gcc 的对照（漏报是否也算 gcc 的盲区）

对 10 个漏报用例跑 `gcc -fsyntax-only -Wall -Wextra`（已过滤掉因缺
`#include` 产生的 implicit-declaration 噪音）：

| 用例 | gcc 诊断 |
|---|---|
| `err_02_scan_missing_amp.c` | ⚠️ `format '%d' expects argument of type 'int *', but argument 2 has type 'int'` |
| `err_05_char_int_confusion.c` | ❌ error: `assignment to 'char' from 'char *' makes integer from pointer without a cast` |
| `err_20_pass_array_by_index.c` | ❌ error: `passing argument 1 of 'sum_all' makes integer from pointer without a cast` |
| `err_03_off_by_one.c` | 无 |
| `err_04_loop_never_advance.c` | 无 |
| `err_12_reverse_index.c` | 无 |
| `err_15_uninit_arr_read.c` | 无 |
| `err_16_string_no_terminator.c` | 无 |
| `err_22_missing_return.c` | 无 |
| `err_28_infinite_loop.c` | 无 |

**结论分两半**：

- **gcc 能报而 csub 漏报的 3 条**（02、05、20）——这三条是**类型系统
  信息不足**导致的真缺口，因为 gcc 有完整的类型树而 csub 的类型推导
  在表达式层就退化成一个字符串。这是 csub 相对 gcc 的真实劣势，
  修的价值也最高（这三类都是学生高频错误）。
- **gcc 也一声不响的 7 条**（03、04、12、15、16、22、28）——这些恰好
  落在 csub 的产品定位上：**「把能编译但会出事的代码拦下来」**。
  死循环、循环边界、未初始化数组元素，gcc 全部放行，而它们正是
  学生作业里最难自查的 bug。这一批应该是 csub 的差异化价值所在，
  而不是「和 gcc 一样就算合格」。

## 6. 给后续轮次的建议（按性价比排序）

1. **把 W8 推广到所有非 void 函数**（`src/semantic.py:379`）。
   `block_returns()` 已经写好了，只是被 `fn.name == "main"` 挡着。
   改一行判断，`err_22_missing_return.c` 就能从漏报变检出。
2. **修 `check_assign_compat` 的类型判据**（`:433`）。
   现在只认 float→int；补上 `char* → char` 就能接住 `err_05`。
   同时把 `Str` 的类型从 `"char*"` 之外区分出「字符串字面量」，
   提示语才能说清「字符常量用单引号」。
3. **给 scanf/sscanf 的输出参数分型**（`:1032`）。
   现在是 `i >= 1` 一律当输出。区分「`&x` 形式」与「裸 `x` 形式」：
   前者标记已初始化，后者如果参数类型不是指针，应报「scanf 的输入
   参数需要取地址」。直接修掉 `err_02`，且不会放松对正确写法的容忍。
4. **实参类型比对**（`:1107`）。需要先把「数组实参」的类型信息传下来，
   这是三处类型混淆漏报（02/05/20）的共同根因，改动面最大，
   但收益也最大。
5. **循环边界与死循环**（4 条漏报）。需要区间分析或至少「循环条件里的
   自由变量是否在循环体内被修改」这种轻量检查。工作量最大，
   但这是 gcc 完全不管、而学生最痛的一类。
6. **W5 的浮点提示语分流**（`:527`）。低成本，纯文案修正，
   但直接影响学生对提示的信任度。
